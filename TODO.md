# GIT G.O.A.T. Delivery Outcomes

- [ ] **Repository-agnostic app and API** — Accept an authorized GitHub repository URL without hardwiring to any specific repository; provide a frontend and reusable REST API with request validation, consistent errors, authorization checks, rate limiting and API versioning. Validate any claimed Bit components/commands against actual installed tooling; do not leave unresolved imports.
- [ ] **Minimal branded entry and service-backed dashboard** — Use the supplied artwork as the page background and make repository submission the primary action. Show scan progress, inventory, evidence-backed findings and severity breakdowns, dependency/security and missing-functionality reports, import graph when supported, approval queue, execution/repair history, PR state, tests, verification, completion percentage and downloadable report. Display only persisted/backend-derived states; do not fabricate values.
- [ ] **Read-only repository scanning** — Initial scan must never execute repository code or modify repository contents. Support public repositories without OAuth and authorized private repositories; resolve and record a commit identifier; reject archives larger than 200 MB; record complete inventory and exclusion reasons; inspect documentation/configuration/CI; analyze JS/TS imports/dependencies when supported and provide generic inventory/security/docs/CI/config analysis otherwise; run deterministic analysis rules and evidence-backed findings.
- [ ] **Enterprise readiness and completion scoring** — Use fixed weights Critical=10, High=6, Medium=3, Low=1; calculate verified completion as weight(VERIFIED_COMPLETE)/weight(in-scope)×100. Only VERIFIED_COMPLETE counts; IMPLEMENTED_UNVERIFIED does not; BLOCKED stays blocked; NOT_REQUIRED requires documented justification; user exclusions require at least 10 characters and appear in the report. Never inflate scores by excluding unresolved work. Same commit and model version yield deterministic analysis.
- [ ] **Guided completion flow** — Explain remaining work, tips and pointers; provide a step-by-step multiple-choice workflow for resolving findings; preserve status, origin scan/commit, rationale, user choices and evidence; make unresolved items and approval boundaries explicit.
- [ ] **GitHub OAuth and authorization** — Implement the requested callback `/goat-service/auth/callback`; request least privilege incrementally for public and private repository access; use server-side protected credentials, CSRF/state validation, encrypted token storage, secure sessions, repository authorization checks, connection status and logout. Public scanning must work without OAuth configuration. Provide bounded transient retry handling without blindly replaying writes.
- [ ] **Vercel Sandbox connection and isolated execution** — Provide a real server-side credential/project check with accurate configured/reachable/failed status and retryable, bounded handling for transient connection failures. Run repository code only in the isolated Vercel Sandbox after the user has answered the guided questions for the selected finding; those answers authorize the exact patch and its checks. Do not pass repository/provider/production secrets into the sandbox; limit network, resources, duration and job scope; record redacted evidence and clean up. A failed or unavailable runner must block PR creation and be reported accurately.
- [ ] **Q&A-authorized repairs and pull requests** — For the selected finding, the user's guided answers authorize only that specific remediation; do not treat them as blanket permission for unrelated edits. Generate a patch, run applicable checks in an isolated Vercel Sandbox, retain redacted diff/log evidence, then automatically push the Q&A-authorized change to a dedicated `goat/repair-*` branch and create or update a PR. If checks fail or the runner is unavailable, do not claim success or automatically open the PR; report the blocker. Never merge or deploy automatically. Never pass GitHub credentials, provider secrets, or production credentials into the sandbox. Preserve user files, keep production configuration/credentials/authorization/deployment changes out of automatic repairs, originate work from the scanned commit, and include rollback guidance.
- [ ] **Tests and verification evidence** — Run applicable tests/build/lint in isolation after repair, rescan the repair branch, compare findings, check new vulnerabilities, verify actual commit/files and produce a final evidence report. Keep unexecuted checks IMPLEMENTED_UNVERIFIED. Add and execute unit, integration, API, auth/permission, public/private repo, read-only/no-initial-execution, sandbox/network/resources, approval, repair/PR, persistence, scoring, rescan, frontend and security regression tests. Never claim a test passed without execution evidence.
- [ ] **Neon connection and persistence** — Use Neon Postgres for durable connector state, repository connections, scans/commits, inventories, findings/severity/exclusions, Q&A authorizations, sandbox jobs/log references, repair orders, branch/PR references, test results, before/after comparisons, verification evidence and audit history. Verify reachability with a bounded `SELECT 1`; report transient/permanent failures accurately and offer bounded retry. Include schema migrations, indexes, validation, error handling and retention controls. Public read-only scans remain available without Neon; never claim durable state until connected and exercised.
- [ ] **Connector chooser, status, errors, and retry UX** — Provide a visible Connectors control where the user can choose GitHub, Vercel Sandbox, and Neon independently. Show actual server-derived connection state, permission scope, last check, and actionable errors; distinguish selected from connected. Request protected credentials only when needed and keep them out of frontend and execution jobs. Provide retry for safe connection checks with bounded backoff, cancellation, and no blind retries for branch/PR writes. Do not create provider resources or incur usage charges without separate user confirmation. With required connectors missing, keep write/execution actions disabled and explain what is needed.
- [ ] **API documentation and reports** — Document authenticated/versioned endpoints for auth/connections, repository registration, scans/status/findings/inventory/dependencies, approvals, sandbox, repair proposals/branches, PRs, tests, verification/rescans and reports. Final report covers component/file inventory, implemented/missing features, security/auth/sandbox assessment, endpoints, schema/persistence, test evidence, deployment readiness, blockers, verified score, commit and evidence per PASS. Use only PASS, FAIL, BLOCKED, NOT RUN, IMPLEMENTED_UNVERIFIED, NOT REQUIRED.
- [ ] **Installation/configuration/deployment** — Provide correct setup, database, configuration and deployment instructions for the actual implementation; support requested Bit commands only if compatible and verified. Preserve existing work and report exact tested commit.
